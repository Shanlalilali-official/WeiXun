# 张建国 DeepSeek 空白响应诊断

## 结论

旧版实测中的 4 条异常，采样器保留的 rawOutput 只有空格：原始值分别为 21、17、16、17 个空格。调用方随后把它们当作 JSON 正文解析，结果记为 invalid_json，所以表现为回应失败。空白字符串不是NPC回复。

这解释了错误如何出现，但还不能说明模型为什么返回空格。原始四次请求没有保存 HTTP 状态、finish_reason、服务端返回的 model、usage 或 reasoning_content。后续精确复测四次均得到有效 JSON；另一组 8 条对照中出现 1 条空格响应。现有证据不足以把某个模型参数或提示词句子认定为已证实根因。

2026-10-14 的 v5 直连提示词抽样中，DeepSeek 四条样本都被归为 invalid_json。采样器保留的 rawOutput 长度如下：
| 样本 | rawOutput |
| --- | --- |
| 中档开场 | 空格 × 21 |
| 高档开场 | 空格 × 17 |
| 低档敏感拒绝 | 空格 × 16 |
| 低档长篇推销 | 空格 × 17 |

该次运行没有保存完整 API 响应元数据，不能倒推出这四次的 HTTP 状态、结束原因、服务端模型字段或推理模式。详见 [v5-live 摘要](../harness/evidence/npc-zhang-natural-replies-2026-10-14/v5-live/summary.json)。

## 可确认的问题与不能确认的原因

1. **可确认的解析问题：** 空格字符串没有正文。旧路径没有先用 trim() 区分空白内容，空格未被作为空响应处理，随后触发 JSON 解析失败并被记为 invalid_json。建议将“模型无正文”和“正文不是合法 JSON”分开记录；保留原始响应，空白单独归类为 blank_content。
2. **可确认的提示词缺陷：** v5 系统提示要求“不输出 JSON”，调用端却启用 JSON mode 并要求外层 {content}。两条指令冲突，值得修正。2×2 对照里兼容协议的四条均有效，但 v5 冲突组也有三条有效；这说明冲突是实际缺陷和风险因素，却没有证明它是四条原空白的唯一原因。
3. **模型侧原因尚未确认：** 精确复测四条全有效，2×2 对照只有一条空白；原四次又没有 HTTP 和结束原因元数据。因此不能判断每条原始失败是由 thinking 默认状态、提示词冲突、服务端偶发空输出或其他因素造成。DeepSeek 官方 JSON mode 文档也提到 JSON 模式可能偶尔返回空内容，并建议在提示中包含 JSON 格式示例及合理的 max_tokens 设置；这是一般已知风险，不是本批请求的单因果证据。[JSON Output 官方文档](https://api-docs.deepseek.com/guides/json_mode/)
4. **thinking 不能单独定因：** 官方文档说明 thinking 默认开启，并将 reasoning_content 与最终 content 分开返回；thinking 模式下温度参数不生效。因此温度 0.7 下的默认 thinking 与 disabled 不是仅改变一个等价生成条件。此次对照不足以把其中一个状态判为故障根因。[Thinking Mode 官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)

## 与实际拜访链路的参数区别

两组直连诊断都不是完整游戏 UI 拜访，也没有测试预约流程或服务端结束状态。精确复测及 2×2 对照使用温度 0.7、JSON mode、未传 max_tokens；精确复测省略 thinking 参数，2×2 则显式比较默认与关闭。

当前正式拜访流式调用使用温度 0.7、thinking disabled、未传 max_tokens。预览结构化调用使用温度 0.35、max_tokens=3000、JSON mode、thinking disabled。因而本报告直连复测没有完整覆盖正式链路，也不是预览链路的同参数复现。max_tokens=3000 是预览请求的 token 上限，与日常正文 35 字软参考不是同一种限制。

## 建议

保留 v6 的 JSON 单字段协议和当前身份锁定提示；诊断上把空白内容单独分类，并在后续真实预览/拜访运行中保存原始响应、HTTP 状态、request-id、返回 model 字段、finish_reason、usage 和 reasoning_content 长度。后续对照应使用一致的人物主档标题和相同链路参数，再判断是否需要进一步修改提示或模型设置。不要把本次 4/4 精确复测成功解释为原故障已根治。
