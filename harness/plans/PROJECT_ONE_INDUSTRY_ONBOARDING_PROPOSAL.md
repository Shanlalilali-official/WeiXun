# 项目一行业/业务选择与开场简报方案（2026-11-06，待用户定稿）

本轮范围：用户要求先讨论需要考虑的事项、确定方案，再制作几份前端示例HTML供选择。本轮仅代码只读核查、公开资料调研和方案记录；未改产品、未调用真实模型生成场景、未写远程数据库，尚未制作HTML。

## 用户已明确

- 进入项目一有总体介绍弹窗，可带美观前端动效。
- 玩家选择客户行业、自己公司的业务；采用选项形式，目录由本轮提出建议。
- AI提前生成匹配行业/业务的具体项目信息，保存在数据库；开局匹配后直接取用，不等待现场生成。
- 选择完成后展示具体项目背景与客户人物介绍；人物仅照片、姓名、职务。
- 延续此前要求：玩家端与实际测试端的业务内容和逻辑一致；其他需要搜集的信息不因开场介绍免费披露。
- 用户补充：供方产品、案例、能力和交付情况由玩家结合自己真实公司考虑；系统重点准备适配度较高的客户方。主营业务选择仅作客户需求匹配标签，不据此生成我方能力档案，也不增加必填公司资料。
- 用户进一步明确：以目前系统的项目信息表为基础，做更完整、详细、专业的AI生成版；客户谈到技术细节时，要有可依赖的客户项目事实支撑。

## 建议的玩家流程

同一个大型弹窗分两步切换：

1. 简短说明项目一训练任务；以卡片选择客户行业和我方主营业务。业务可以在卡片内展开具体方向，但首版每局只选一个主方向。客户单位性质（如国企/民企/事业单位）由场景给出，不与行业混作同一级选项。
2. 展示匹配的客户项目简报：客户概况、项目起因、现状问题、公开需求/范围、已知预算或“待确认”、客户时间要求和验收目标；同页展示五人照片/姓名/职务。玩家自行结合公司实际产品/服务制定推进方案，系统不提供虚构我方产品、案例或交付能力。提供返回调整和“开始训练”。

行业/业务只显示已有已发布场景可覆盖的选项；无匹配时明确暂未开放，不暗换其他行业或现场临时生成。动效建议选中反馈、内容切换和人物卡渐次出现，短而可跳过，尊重减少动效偏好。只在最终点击开始训练后启动20分钟倒计时；阅读、选择、动画不消耗AP。已有存档恢复直接续关，按原场景版本读取，不重新选择或抽取。

## 场景库与后台

建议后台流程：选行业/业务及难度约束 → AI批量生成结构化草稿 → 自动校验 → 后台预览/编辑/审核 → 发布 → 开局匹配。生成失败可单项重试，未发布内容不进入玩家匹配；同组合可以有多个项目版本。

一份客户场景资料应包含：

- 公开项目背景：虚构客户单位、行业/性质/规模、项目起因、公开需求、采购范围、已公开预算/进度、交付要求。
- 客户适配信息：与主营业务标签相关的需求方向、现有设备/系统或工作方式、期望改善的结果、预算/接口/工期等客户约束、可接受的方案范围。需求写得具体，保留多种产品/服务路线，不绑定某品牌、型号或虚构供方。
- 人物场景映射：复用既有五人稳定ID、照片、姓名，按行业映射职务/部门和职责语境。例如医院分管负责人、信息部门项目负责人、采购负责人；具体是否改职务待用户确认，不能只改开场称谓而保留矛盾的NPC提示。
- 受控隐藏内容：后续可搜集事实、个人诉求、内部关系/决策倾向、真正预算和评分依据等，明确披露边界，不放入开场人物卡。
- 版本/发布与约束：行业/业务代码、模板ID/版本、难度、状态、生成批次及配置来源、校验/审核结果。客户预算、采购范围、现状、人物称呼、竞品情况和验收条件需要一致。

客户NPC和评价应根据客户需求、玩家实际提出的方案与可验证证据判断匹配程度/可行性，不用未提供的我方产品档案作评分依据。玩家表述的产品能力/案例可作为本人陈述保留、继续询证，不由AI补写成已核实事实。不额外要求开局上传公司资料。

开局冻结同一客户场景版本/内容快照。开场、左侧项目资料、NPC对话上下文、可搜集线索、客户预算、竞品情况及场景约束都引用同一份，不可仅替换文案；我方真实能力不由此快照虚构。正式玩家与实际测试共用场景解析/匹配服务，测试可指定同一模板版本复现。首版建议固定同一训练难度，行业/业务选择不自动变成难度选择；不擅改原AP/20分钟/评分规则。现有固定供应商优势/结算常量后续需核对与开放供方定位的关系，本轮不据此自动改胜负公式。

若支持多人，同房间共用客户与项目快照，各玩家仍结合自己公司的实际情况提出方案。本条为兼容设计考虑，不扩大本轮为多人功能实现。

## 现有项目信息表的专业AI生成版（用户明确方向）

已定位具体参照：`projects/src/app/designer/client-info/page.tsx:15`的甲方项目信息表，及`src/lib/designer/excel-data.ts`的clientInfoRows。现有R1–R17包含项目名称、规模、采购/投运时间、最终使用者、设计单位、技术难点/要求、预算/资金来源、决策方式、验收标准、供应商要求、历史合作、立项原因、发展规划、领导关注点。以这些字段为骨架扩充，不另造互不相干的资料表；编号作展示，内容引用应采用稳定字段键。

建议扩充为“通用项目字段＋按行业/业务匹配的技术细节”：

| 分组 | 应生成的客户侧事实 |
|---|---|
| 客户与项目基本情况 | 行业、单位性质、规模/地点、相关部门、最终使用者、立项原因、建设范围及不在本次范围的事项 |
| 业务现状与痛点 | 现有流程、涉及岗位、工作量/业务规模、具体问题、影响、优先级和历史尝试 |
| 现有技术环境 | 已有系统/设备及必要版本、部署位置、网络/运行环境、数据种类与规模、在用方式和已知限制 |
| 需求与技术约束 | 要实现的能力、必须/可选要求、接口与兼容条件、数据或设备接入、性能/容量、安全与运行约束 |
| 实施与协作条件 | 采购/投运节点、客户配合部门、现场或迁移条件、停机窗口、分期安排、责任边界、培训和运维诉求 |
| 预算与采购 | 客户预算口径、资金来源、采购方式、供应商要求、历史合作和公开/非公开边界 |
| 验收与成功标准 | 可检查的交付物、测试条件、指标及单位、验收方法/责任岗位、失败整改与后续服务要求 |
| 决策与信息边界 | 各人职责、关注点、哪些事实谁知道/何时可披露、待确认事项，避免把后台完整性等同于开场全公开 |

字段应贴合业务：软件侧可深入系统/接口/数据迁移，设备侧可深入现场/既有设备/运行条件，服务侧可深入范围/时限/交付标准。客户技术资料不替玩家生成其公司能力；客户追问供方参数/做法时仍需玩家按实际情况回答。

生成和使用要求：

- AI提前一次性生成同一版本的结构化完整底稿；开场简报从公开字段生成摘要，NPC从同版底稿按职责和披露规则取事实，玩家端/实际测试共用。
- 针对常见技术追问准备参考问答和对应事实字段，回答依据来自底稿，不用问答内容反向补造未定义事实。发布前检查数字/单位、预算与采购范围、规模与容量、工期与实施安排等前后一致性；后台可预览、修改和审核。
- 记录“已知/待确认/未定义”。运行中底稿未提供的技术参数可回复需要核实，不为显得专业即兴编造型号、接口、性能或承诺。
- 深度按角色适配：高层仍聚焦目标/投入/风险；项目负责人讨论技术/交付/验收；执行岗位讨论现场流程与使用；招采讨论采购和预算边界；综合协调岗位按其职责。共享底稿不使所有NPC成为全知技术专家，不覆盖既有人物职责规则。
- 客户档案保持具体且允许多种可行方案，不写成唯一品牌/型号才能满足的虚构招标指向。评价依据客户需求和玩家实际方案/证据，不使用不存在的我方预设档案。

此处为方案补充，尚未生成实际档案、修改当前表或游戏。现有client-info页面使用默认行和Excel导入本地草稿，尚不能作为已贯通两端的服务端专业知识库；后续实施要连接前述版本发布/数据库持久化，而不只增加页面文字。

## 后续HTML选择阶段

用户定稿后，用同一套内容和两步流程制作3份独立可打开的HTML：

1. 作战简报：深蓝、聚焦项目任务和人物卡，轻微入场动效。
2. 商务工作台：浅色、清晰选择卡片与分步进度，克制的内容切换。
3. 行业场景：行业视觉和较大项目封面，人物卡渐次展开。

三份均需可选择行业/业务、返回修改、查看同一项目背景与五人、跳过动效，并适配常见屏幕。示例先用标明演示的本地数据和已有照片，选样式阶段不接真实生成/数据库或改变正式游戏；选定视觉后再接完整产品链路。

待用户确认两点：首版业务范围是否按信息化/数字化起步；五人照片/姓名保留、职务随行业适配是否采用。
